# Artifact attestation policy

**Status:** PROPOSED
**Authority effect:** NONE
**Implementation:** NOT ENABLED
**Policy version:** 0.1
**Documentation checked:** 2026-07-27 (SLSA v1.2, GitHub Actions, GitHub CLI 2.96.0)

This policy separates release provenance from authorization. A build
attestation can bind an artifact digest to build provenance. It is not a Permit,
merge decision, release decision, correctness proof, safety claim, or adoption
signal.

```text
attestation != Permit
provenance != authorization
verified identity != semantic truth
```

## Standards baseline and claim status

This policy is aligned to the approved SLSA v1.2 specification terminology and
the SLSA Provenance v1 predicate:

```text
in-toto statement type: https://in-toto.io/Statement/v1
predicate type:         https://slsa.dev/provenance/v1
current project level:  NOT_ASSESSED
initial target:         SLSA Build L2 candidate
Build L3 claim:         FORBIDDEN without separate platform assessment
```

SLSA Build L1 requires provenance that identifies the output by cryptographic
digest and describes how it was produced. Build L2 adds authentic provenance
generated by a hosted build platform and consumer verification. Build L3 adds
stronger build-platform isolation and tamper resistance. Merely using a
workflow, a reusable workflow, or GitHub's `attest` action does not authorize
this repository to self-declare a level.

GitHub currently documents that its artifact-attestation mechanism by itself
maps to SLSA v1.0 Build L2, and that reusable workflows can support a v1.0
Build L3 design. This project still records its own level as `NOT_ASSESSED`
until its release workflow, build platform, verification policy, and operational
controls have been reviewed against the selected SLSA version. The GitHub
v1.0 mapping is not silently translated into a project claim under SLSA v1.2.

## Current pass

- Pull-request CI must not request attestation or OIDC permissions merely to
  decorate candidate artifacts.
- Candidate packages remain non-release outputs until a separate release
  decision identifies the exact source commit and artifact bytes.
- No GitHub Actions attestation workflow is enabled by this document.
- No signature, transparency-log entry, release, push, or deployment is
  authorized.

## Eligibility for a future release attestation

An artifact becomes eligible only when all of the following are recorded:

1. an explicit release decision names the exact source commit;
2. deterministic packaging produces the exact candidate bytes;
3. the artifact SHA-256 and exact manifest-byte SHA-256 are recorded
   separately;
4. the release workflow identity and policy are pinned;
5. the repository's protected release path and required reviewers are
   independently confirmed;
6. a verification procedure and expected identity are documented before
   publication.
7. the release runner is GitHub-hosted unless a separate self-hosted runner
   assessment is approved;
8. every top-level external parameter that can influence the build is declared
   and treated as untrusted during verification.

Mutable acceptance or promotion status must not be embedded inside the
artifact's content identity. Acceptance remains an external, versioned
transition record.

## Required future provenance envelope

The primary subject is the exact distributable ZIP, identified by SHA-256.
Attesting the package does not silently attest every claim inside it.

The in-toto/SLSA statement must expose:

- `_type: https://in-toto.io/Statement/v1`;
- a `subject` entry containing the exact package name and SHA-256;
- `predicateType: https://slsa.dev/provenance/v1`;
- `predicate.buildDefinition.buildType`;
- all top-level `externalParameters`;
- `resolvedDependencies` including the source repository and full commit;
- `runDetails.builder.id`;
- the workflow invocation identity and timestamps when provided by the build
  platform.

The package-manifest root and packaging-policy version may be recorded as
declared metadata or resolved dependencies only when their meaning is explicit.
They are not part of the package subject digest unless those bytes are inside
the package. The manifest's exact-byte SHA-256 remains a separate commitment.

## Generation controls

A future release job must:

1. be separate from pull-request validation and non-release candidate jobs;
2. start only after a recorded release decision identifies the exact full
   commit and expected package identity;
3. check out that exact commit with persisted Git credentials disabled;
4. build through the reviewed deterministic package builder;
5. fail if the package or manifest digest differs from the release decision;
6. grant `contents: read`, `id-token: write`, and `attestations: write` only to
   the attestation job;
7. attest the exact distributable path after all build and digest checks;
8. upload or publish only the same bytes named as the attestation subject;
9. retain the attestation bundle or a documented retrieval path with the
   release record.

No mutable acceptance field belongs in the package identity or provenance
predicate. Release acceptance remains a detached transition record.

## Verification

Publication alone is insufficient. A consumer must verify the artifact bytes,
predicate type, repository, signer workflow, source commit, hosted-runner
policy, and any producer-defined external-parameter expectations.

The future public verification form is:

```text
gh attestation verify <artifact.zip> \
  --repo XRastlinX/logos-formal \
  --signer-workflow XRastlinX/logos-formal/.github/workflows/<release-workflow>.yml \
  --signer-digest <full-signer-workflow-commit> \
  --source-digest <full-source-commit> \
  --predicate-type https://slsa.dev/provenance/v1 \
  --format json \
  --deny-self-hosted-runners
```

The workflow path remains a placeholder until the release workflow is
separately reviewed and authorized. Verification output should be retained as
a detached receipt. A successful verification establishes only the bounded
provenance claims checked by that command and follow-on policy.

The CLI verifies the signed subject and selected identity constraints. It does
not by itself establish that every producer-controlled predicate field is
trustworthy. Follow-on policy must inspect the JSON verification result and
reject unexpected `buildType`, `externalParameters`, source dependency,
builder, signer, or subject entries. Trusted-builder isolation requires a
separate platform assessment.

## Failure posture

Missing attestation, subject mismatch, unexpected workflow identity, ambiguous
policy, or failed verification yields `NO_DECISION` for provenance acceptance.
It does not authorize an effect and it does not rewrite the artifact.

## Acceptance checklist

The policy is ready to move from `PROPOSED` only after a reviewer can answer
yes to each item:

- release event and accountable decision are defined;
- exact source, package, and manifest commitments are bound;
- build type and external parameters are documented;
- builder and signer workflow expectations are pinned;
- permissions are job-scoped and absent from ordinary PR CI;
- verification is tested against success, wrong artifact, wrong repository,
  wrong signer workflow, wrong source commit, and self-hosted runner cases;
- lifecycle and revocation handling are documented;
- no text equates attestation with Permit, correctness, safety, or authority.
