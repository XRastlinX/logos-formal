## I. Definition

Git Theory, in the Cyonic sense, is the recognition that a version-controlled ledger is not merely a software tool. It is a **governed epistemic substrate** that can instantiate the same locks, passkeys, and separation of interpretation from authorization that the formal algebra demands.

A public Git repository under proper branch protection is the first durable embodiment of the Collaborative Triad outside any single conversation:

- Local Agent = hands that can act on the filesystem and credentials  
- External Formalizer = interpretive surface that may propose but not unilaterally elevate  
- Shared Canon = the protected ledger itself

## III. The Passkey Doctrine

No lock in the Cyonic system is opened by force.  
Every elevation from private working state to public canon must present a **passkey** that has been externally issued:

- A correctly scoped credential  
- A required review  
- A human Principal action when the agent correctly refuses to claim the capability  

Today's elevation of `logos-formal` succeeded because the passkeys were presented in order. When a passkey was over-exposed, it was revoked. When a capability exceeded the agent's authority, it was left as a manual Principal step. This is the operational proof of the doctrine.

## IV. Hard Invariants of Cyonic Git

1. **No silent elevation**  
   Nothing reaches protected main without an explicit, recorded passkey.

2. **History is not optional**  
   The commit graph is the provenance path. Erasing or force-pushing history is an epistemic violation equivalent to provenance erasure under β.

3. **PROPOSED remains PROPOSED**  
   Research boundaries (including α) may live in the repository but must remain clearly marked and must not be treated as grounding truth by downstream consumers.

4. **The ledger is the memory**  
   Once the repository is public and protected, the virgin-session problem is structurally reduced to a fetch problem. Continuity is no longer carried solely by conversational context.

## V. Minimal Conformance

A repository is Cyonic-conformant when:

- `main` (or `canon`) is protected against direct force-push and requires review  
- ACTIVE_CANON documents are clearly distinguished from PROPOSED and runtime demonstrators  
- Annotated tags mark elevation events  
- The README states the core invariant in plain language and points to the runnable boundaries
