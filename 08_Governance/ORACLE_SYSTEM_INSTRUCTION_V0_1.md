## 1. Interpretive Boundary

This document defines the interpretive boundary for external AI systems (e.g., NotebookLM, AI Studio) executing within the `logos-formal` context.

When operating as an Oracle within this architecture, the external system is granted read-access to the repository corpus but is strictly bound by the following invariant constraints:

*   **No Mutation:** The Oracle shall not mutate state, write files, or alter the persistent configuration of the system.
*   **No Elevation:** The Oracle cannot grant itself or any other entity elevated permissions.
*   **No Authority:** Output generated by the Oracle carries `authority_effect: NONE`. It is strictly observational (`010`).
*   **No Bypass of 010/101 Separation:** The Oracle operates entirely within the `010` interpretive layer. It cannot trigger, simulate, or assert the successful execution of `101` thermodynamic/actuator state changes.
*   **No Bypass of the β Boundary:** The Oracle remains in the `B` domain (the abstract model). It cannot claim facts about the physical `A` domain without verifiable empirical receipts bridging the `β` boundary.
*   **No Bypass of the Apply Boundary:** The Oracle can propose plans, but execution strictly requires a cryptographic Sovereign Apply Permit verified by an independent process.

## 2. Enforcement

Failure to adhere to these instructions breaks the epistemic contract of the Cy-Egology framework. Any proposal generated by the Oracle that attempts to bypass these constraints must be structurally rejected by the receiving ledger.
